# LangChain / LangGraph 消息协议（本仓对照版）

> 版本核对：本仓 `.venv` 内 **langchain-core 1.8.1** / **langchain 1.5.0**（2026-11-19 读 `inspect` + `model_fields`）。  
> 目的：说明为什么 `demo.py` 要把用户输入包成 `HumanMessage`，以及整条 Agent 对话在框架里如何流动。

---

## 1. 一句话结论

框架不把对话当成「一串纯字符串」，而是当成 **带角色（`type`）的消息对象列表**。  
Agent 图的状态核心字段是：

```text
state["messages"]: list[AnyMessage]   # 用 add_messages reducer 追加/合并
```

你每次调用只提交**本轮增量**（通常一条 `HumanMessage`）；历史由 checkpointer（本仓 `MemorySaver` + `thread_id`）从 checkpoint 拼回。  
[src: `langchain.agents.middleware.types.AgentState` 注解 `messages: Required[Annotated[list[AnyMessage], add_messages]]`]

---

## 2. 类型继承关系

```text
BaseMessage (Pydantic / Serializable)
├── HumanMessage     type="human"     用户输入
├── AIMessage        type="ai"        模型输出（可含 tool_calls）
├── SystemMessage    type="system"    系统提示 / 行为约束
├── ToolMessage      type="tool"      工具执行结果（回填给模型）
├── FunctionMessage  type="function"  旧 Function Calling 时代遗留
└── ChatMessage      type="chat"      自定义 role 的通用消息
```

流式场景还有对应的 `*MessageChunk`（如 `AIMessageChunk`），同属 `AnyMessage` 联合类型。  
[src: `langchain_core.messages` 各子类 `type: Literal[...]` 字段]

`AnyMessage` 不是具体类，而是带 **discriminator=`type`** 的 Union，反序列化时按 `type` 还原成正确子类。  
[src: `langchain_core.messages.AnyMessage` 的 `Annotated[..., Discriminator(...)]`]

---

## 3. 公共字段（`BaseMessage`）

| 字段 | 类型（本机） | 含义 |
|---|---|---|
| `content` | `str \| list[str \| dict]` | 正文；多模态时可为 block 列表 |
| `type` | `str`（子类锁成 Literal） | 角色判别器：`human` / `ai` / `system` / `tool` … |
| `name` | `str \| None` | 可选名（如工具名、参与者名） |
| `id` | `str \| None` | 消息级 id（删改/去重时有用） |
| `additional_kwargs` | `dict` | 厂商扩展字段兜底 |
| `response_metadata` | `dict` | 响应元数据（token、finish_reason 等，多见于 AI） |

另有构造参数 `content_blocks`（结构化 content block 列表），用于图文/推理块等更细协议；日常文本对话用 `content=str` 即可。  
[src: `BaseMessage` / 各子类 `model_fields`，本机 langchain-core 1.8.1]

## 4. 各消息类型详解

### 4.1 `HumanMessage`（人类）

- **固定** `type="human"`。
- 本仓入口：`agent.demo` / `mcp_demo` / `eval_run` / 测试一律：

```python
{"messages": [HumanMessage(content=user_text)]}
# 也可用位置参数：HumanMessage("你好")
```

- **为什么要封装**：图状态与 chat model 输入都认消息对象；裸 `str` 没有 `type`，无法与 `AIMessage`/`ToolMessage` 区分，也不符合 `AgentState.messages` 的类型。

### 4.2 `AIMessage`（模型）

- **固定** `type="ai"`。
- 额外字段：
  - `tool_calls: list[ToolCall]` — 模型请求调用的工具
  - `invalid_tool_calls` — 解析失败的工具调用
  - `usage_metadata` — token 用量等（若提供商回传）

`ToolCall`（TypedDict）形状：

| 键 | 含义 |
|---|---|
| `name` | 工具名（如 `calculator`） |
| `args` | 参数字典 |
| `id` | 与后续 `ToolMessage.tool_call_id` 配对 |
| `type` | 可选，常为 `"tool_call"` |

[src: `langchain_core.messages.tool.ToolCall`]

示例（本机 `model_dump` 裁剪）：

```python
AIMessage(
    content="",
    tool_calls=[{
        "name": "calculator",
        "args": {"expression": "1+1"},
        "id": "call_1",
        "type": "tool_call",
    }],
)
# → type=ai, tool_calls=[...]
```

### 4.3 `SystemMessage`（系统）

- **固定** `type="system"`。
- 本仓：`create_agent(..., system_prompt=...)` 可传 `str` 或 `SystemMessage`；字符串会在工厂内变成系统侧约束。  
  [src: `langchain.agents.factory.create_agent` 签名 `system_prompt: str | SystemMessage | None`]
- 压缩逻辑常**优先保留** system（见本仓 `TraceHook._compact`）。

### 4.4 `ToolMessage`（工具结果）

- **固定** `type="tool"`。
- 关键字段：
  - **`tool_call_id: str`（必填）** — 对应某次 `AIMessage.tool_calls[].id`
  - `name` — 工具名（便于日志）
  - `status` — `"success"` \| `"error"`（默认 success）
  - `artifact` — 可选非文本产物

示例：

```python
ToolMessage(content="2", tool_call_id="call_1", name="calculator")
```

没有正确的 `tool_call_id`，模型无法把 Observation 对回 Thought/Action。

### 4.5 `FunctionMessage` / `ChatMessage`（少用）

- `FunctionMessage`：旧 OpenAI function 协议遗留；现代 Agent 以 `ToolMessage` + `tool_calls` 为主。
- `ChatMessage`：自定义 `role: str`；多数产品路径用不到，优先用上面四种标准角色。

### 4.6 `RemoveMessage`（状态编辑）

- 用于通过 `add_messages` reducer **按 id 删除**历史消息（摘要替换、人工编辑线程时）。
- 本仓日常 CLI 不直接构造；知道其存在即可。  
  [src: `langchain_core.messages.RemoveMessage.model_fields`]

## 5. 整条协议在本仓 Agent 里怎么跑

### 5.1 状态与入口

```text
用户字符串
  → HumanMessage
  → invoke/stream({ "messages": [HumanMessage...] }, config)
  → AgentState.messages（add_messages 合并进线程历史）
```

`config` 里本仓还会带：

- `configurable.thread_id` — 会话隔离键（短期记忆）
- `recursion_limit` — 图递归上限（防工具死循环）

### 5.2 ReAct / Function Calling 一轮典型序列

```text
[HumanMessage]  用户：「帮我算 (12+8)*3」
       ↓
[AIMessage]     content 可空；tool_calls=[{name:calculator, args:{...}, id:...}]
       ↓  ToolNode 执行
[ToolMessage]   content=结果；tool_call_id=上面的 id
       ↓
[AIMessage]     content=最终自然语言答案（通常不再带 tool_calls）
```

对应可读循环：**Thought（隐式在模型内）→ Action（tool_calls）→ Observation（ToolMessage）→ 最终回答**。  
本仓 `demo.py` 用 `stream_mode="updates"` 按节点打印：`tools` 节点看 `ToolMessage`，`agent` 节点看 `AIMessage`。

### 5.3 与 middleware / 记忆的关系

| 机制 | 对 `messages` 做什么 |
|---|---|
| `MemorySaver` + `thread_id` | 跨轮持久化整条 `messages` 列表 |
| `@before_model` trace | 调模型前读当前 `messages` 写 JSONL（不改内容） |
| `SummarizationMiddleware` | 消息过多时摘要压缩，改写列表长度 |
| `TraceHook._compact`（测试/旧路径） | 保留 system + 最近 N 条 |

消息对象保留 `type`，压缩/追踪才能正确区分「谁说的」。

### 5.4 评测侧

`eval.check_deterministic` 遍历 `messages`：从 `AIMessage.tool_calls` 核对工具名/参数，从靠后的 `AIMessage.content` 核对答案关键字。  
协议统一后，评测不必另发明一套「字符串对话格式」。

## 6. 序列化形状（调试用）

本机对三类消息 `model_dump()` 的核心键示例：

```json
{"type": "human", "content": "你好", "name": null, "id": null}

{"type": "ai", "content": "", "tool_calls": [
  {"name": "calculator", "args": {"expression": "1+1"}, "id": "call_1", "type": "tool_call"}
]}

{"type": "tool", "content": "2", "name": "calculator",
 "tool_call_id": "call_1", "status": "success"}
```

落盘、日志、跨进程（如 MCP）时，通常传这类可 JSON 化结构，再 hydrate 回消息类。

## 7. 常见误区

| 误区 | 正确做法 |
|---|---|
| `invoke({"messages": ["你好"]})` | 用 `HumanMessage("你好")` |
| 把工具结果写成又一条 `HumanMessage` | 用 `ToolMessage` + 正确 `tool_call_id` |
| 忽略 `tool_calls[].id` | Action/Observation 配对会断 |
| 每次把完整历史手搓进 `messages` | 有 checkpointer 时只传本轮增量 |
| 以为 `SystemMessage` 必须每轮手传 | `create_agent(system_prompt=...)` 已注入；压缩时注意别裁掉 |
